## 背景

当前 0.2 原型把“清理审查计划”渲染为健康摘要与 AI 分析之间的独立区块。真实仓库测试显示，这个区块视觉上偏重，并且和下方的健康问题列表割裂。下一版交互应当把每个问题卡片作为诊断、影响、动作预览、应用和回退的连接点。

## 目标 / 非目标

**目标：**

- 让 UI 更像“带可执行建议的分析结果”，而不是单独的计划文档。
- 默认状态仍然以先审查为主，且所有动作都必须显式触发。
- 增加可信的写入路径：受影响文件、写入前后标签、应用按钮、成功状态和回退。
- 支持截取真实 Obsidian 弹窗在 UI 改动前后的截图。

**非目标：**

- 全自动清理。
- 默认一次性应用所有健康问题。
- 由 AI 生成写入计划。
- 重写 Markdown 正文中的 inline tags。

## 决策

1. 内联动作面板放在问题卡片内部。

   每个可执行的健康问题在“证据 / 影响 / 建议动作”之后展示“可执行建议”区块。这样用户能保持上下文：动作在视觉上绑定到产生它的诊断。

2. 动作按问题分组，而不是按全局计划分组。

   低频、重复、层级和过细标签问题的动作语义不同。按问题展示动作面板，可以避免通用计划表隐藏上下文。

3. 应用控件必须显式且范围明确。

   主按钮只应用当前问题中已启用的文件变更。次级控件提供“查看影响文件”“复制计划”和“跳过”。只有在动作应用后，弹窗中才出现最近一次清理的回退入口。

4. 回退依赖操作记录。

   已应用的清理动作必须记录每个受影响文件的写入前后标签、操作来源、时间戳和动作标签。回退会反向执行最近一次清理操作，并从操作日志中移除该记录。

5. 视觉状态也是规格的一部分。

   UI 必须支持待审查、可应用、已应用、部分应用、已跳过和可回退状态。第一版高保真稿重点覆盖可应用和已应用状态。

## 风险 / 权衡

- [风险] 用户可能在未理解受影响文件的情况下点击应用。-> 缓解：在应用按钮附近直接展示受影响文件数量和预览。
- [风险] 同一个标签可能以 frontmatter、metadata 和正文 inline text 等不同形式出现。-> 缓解：第一版只写入 frontmatter tags，并在 UI 中明确说明。
- [风险] 批量回退可能与应用后被用户修改过的文件冲突。-> 缓解：保存写入前后快照，并在回退前检测不匹配。
- [风险] 问题卡片过长后会变得密集。-> 缓解：文件预览只默认展示前几个，其余内容放入内联详情区域。
