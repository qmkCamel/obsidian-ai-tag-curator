# Obsidian AI Tag Curator 路线图

更新日期：2026-08-04

## 1. 路线图原则

这个项目的核心定位是 **Obsidian 库（vault）的标签管理与治理工具**，而不是普通的 AI 标签生成器。路线图按这个判断排序：

- 先把当前笔记推荐闭环做稳定；
- 再补上库级标签健康报告，证明它不是一次性打标工具；
- 批量写入必须晚于只读分析和可审查计划；
- 任何会修改用户 Markdown 文件的能力，都必须先有预览、确认和撤销路径；
- 大型库性能优先用缓存、截断和按需扫描解决，暂不引入复杂基础设施。

## 2. 版本边界

### 0.1 体验版：当前笔记推荐闭环

目标：让用户能在真实库中体验“优先复用已有标签”的当前笔记推荐。

状态：已扩展为当前笔记推荐 + 规则版标签健康报告，适合持续试用和小范围反馈。

已具备能力：

- 扫描库中已有标签；
- 使用 Obsidian `getAllTags` 对齐 Obsidian 自身标签面板；
- 读取 frontmatter tags 和正文 inline tags；
- 构建标签索引，包含使用次数、文件数和代表性示例；
- 为当前笔记推荐标签；
- 生成只读标签健康报告；
- 默认优先复用已有标签；
- 允许新标签时，仍然优先复用已有标签；
- 过滤当前笔记已有标签，避免重复推荐；
- 限制当前笔记内容和标签索引上下文，避免把全库 Markdown 全量发给 AI；
- 支持 OpenAI-compatible provider，可配置 DeepSeek、OpenAI 等服务；
- 支持中文、英文和 Auto 跟随 Obsidian 当前语言；
- 推荐请求后台执行，完成后弹出结果；
- 推荐结果包含推荐理由、置信度、相近但未选标签；
- 用户确认前不写入文件；
- 确认后只写入当前笔记 frontmatter `tags`；
- 支持撤销当前笔记最近一次标签修改；
- 提供 dev 模式耗时详情；
- README 提供中英文版本。

持续维护：

- README 的“当前限制”需要在每个阶段完成后同步更新；
- 发布前需要保留自动化验证和真实 Obsidian 库（vault）的手动验收记录。

## 3. MVP 完整版

MVP 完整版不追求批量自动改写，而是完成两个可验证闭环：

1. 当前笔记标签推荐闭环；
2. 库级标签健康报告闭环。

这样用户既能立刻改善单篇笔记，也能看到整个库的标签体系的问题，从而感受到“标签管理与治理工具”和“AI 打标签工具”的差异。

### 3.1 标签健康报告

目标：给用户一个库标签诊断报告，指出标签体系中的真实问题，并把规则证据与 AI 行动建议分层展示。

状态：已在 `0.1.2` 完成。健康报告已经按总览、AI 行动层、规则证据层展示，并支持带文件预览、操作日志和冲突保护回退的受限合并/重命名动作。

范围：

- 新增命令：`分析标签健康度` / `Analyze tag health`；
- 复用已有 tag index，不强制每次全库重扫；
- 如果没有 tag index，后台构建一次索引；
- 输出健康报告 Modal；
- 报告按总览、AI 优先处理项、规则证据明细分层；
- 规则证据按问题类型分组；
- 每类问题给出原因、影响和建议动作；
- 可执行合并/重命名建议需要文件预览、操作日志和回退。

第一版报告类型：

- 低频标签：只出现 1 次或很少出现的标签；
- 近似重复标签：大小写、空格、连字符、单复数、中文/英文混用导致的相似标签；
- 层级不一致：同一主题下层级深度混乱，例如 `ai`、`AI/工具`、`ai/tools` 并存；
- 过宽标签：使用次数很高但语义过泛的标签；
- 过细标签：只服务极少笔记，且命名像一次性描述的标签；
- 命名风格不一致：大小写、语言、分隔符、层级写法不一致。

交互要求：

- 报告顶部展示总体摘要：标签数、使用次数、有标签文件数、风险分组数量；
- 每个问题卡片展示：问题标签、证据、影响、建议动作；
- 建议动作只包括“建议合并”“建议重命名”“建议保留观察”“建议废弃”；
- 每个建议都能复制标签名或搜索该标签；
- 可执行合并/重命名建议可以在文件预览、明确确认、操作日志和回退保护下手动应用；
- 低频观察、过宽拆分、废弃/移除类建议保持只读或人工判断，避免 MVP 阶段引入批量写入风险。

验收标准：

- 在真实库中运行后，能发现至少一类实际存在的标签问题；
- 报告不会阻塞 Obsidian 主界面太久；
- 报告结果与 Obsidian 标签面板大体一致；
- 没有 API key 时也能生成基于规则的基础报告；
- 如果调用 AI 增强分析失败，仍能展示基础报告；
- 运行报告、查看规则证据和生成 AI 辅助分析不会修改任何 Markdown 文件；
- 只有用户显式点击可执行项的应用按钮并确认后，才允许修改 frontmatter tags，且必须可回退。

### 3.2 推荐结果体验补齐

目标：让当前笔记推荐在真实使用中更可信、更稳定。

范围：

- 推荐结果继续过滤当前笔记已有标签；
- 新标签建议必须受“允许新标签”和“新标签严格程度”约束；
- 推荐标签按相关性排序；
- 推荐解释必须使用当前 UI 语言；
- 结果 Modal 在中文界面下不出现不必要的英文混排；
- dev 模式继续展示总耗时和阶段耗时；
- 失败时只显示错误，不写入文件。

验收标准：

- 对已带标签的文章再次推荐，不再推荐已有标签；
- 开启允许新标签时，仍能推荐已有标签；
- 关闭允许新标签时，不出现新标签；
- 中文 Obsidian 中推荐理由和 UI 文案以中文为主；
- 请求慢时不阻塞用户继续编辑。

### 3.3 发布前整理

目标：让项目可以作为 GitHub 上的 MVP 版本展示和试用。

范围：

- 更新 `README.md` 和 `README.zh-CN.md`；
- 补充 DeepSeek / OpenAI-compatible 配置示例；
- 明确当前版本能力和限制；
- 补充本地安装步骤；
- 保留技术方案和路线图链接；
- 跑完整测试和构建；
- 在真实 Obsidian 库（vault）中完成 smoke test；
- 提交并推送 MVP 完整版代码。

验收标准：

- 新用户只看 README 能完成本地安装；
- 用户知道 API base URL、API key、model 应该填什么；
- 用户知道哪些能力还没有做；
- `npm test` 和 `npm run build` 通过；
- 安装到测试库后，四个核心命令可用；
- GitHub 仓库中文档入口清楚。

## 4. 发布进度与后续迭代

### 4.1 已交付：标签清理建议与审查计划（0.1.2）

目标：把标签健康报告从“看问题”推进到“生成可审查的清理计划”，并允许确定性合并/重命名动作在预览、日志和撤销保护下手动执行。

状态：原定 `0.2` 的安全清理闭环已提前随 `0.1.2` 交付，并于 2026-05-26 在真实 Obsidian 库中完成手动验收。

后续扩展状态（2026-08-04）：确定性合并/重命名已实现 occurrence 级 inline token 审查、混合来源 V2 事务、固定目标恢复和跨重载整体回退；自动化验证已完成，真实 Obsidian 多版本与视觉验收仍待执行，不能沿用 2026-05-26 的 frontmatter-only 验收结论。

已交付：

- 从健康报告中选择一组问题；
- 生成标签清理计划；
- 为每条建议标记动作能力，例如仅预览、仅观察、需人工判断；
- AI 增强分析只能补充说明、排序和候选目标，不能提升动作可执行性；
- 展示受影响文件列表；
- 展示每个文件的变更前后标签；
- 支持用户手动应用可执行合并/重命名建议；
- 按文件展示 frontmatter diff 与每个正文 occurrence，允许逐项取消并明确 partial 剩余数；
- 只有当前 `TagCache.position` 精确匹配的完整 token 可写，fallback inventory 只有查看权；
- frontmatter 与 inline token 使用同一条 V2 intent、补偿、固定目标恢复和整体回退记录；
- 为清理写入记录操作日志，并支持回退最近一次清理操作；
- 支持导出计划为 Markdown；
- 支持复制建议操作。

不做：

- 不自动改写全库；
- 不后台静默执行；
- 不做未经 occurrence 审查的正文修改；当前只支持确定性合并/重命名的精确完整 token 替换，不支持新增、删除、拆分、模糊搜索、全局替换或 AI 生成的正文写入；
- 不对低频观察、过宽拆分、废弃/移除类动作提供一键处理；
- 不做复杂规则引擎。

已验证：

- 用户能理解某个合并/重命名建议会影响哪些文件；
- 用户能在写入前放弃任意一条建议；
- 即使不写入，计划本身也能作为人工整理参考。

### 4.2 0.3：文件夹级安全批量预览

目标：允许用户选择一个文件夹，对其中笔记批量生成标签建议，但所有写入必须先经过预览。

状态：已实现。当前笔记与文件夹批次已统一使用整篇标签清单、完整 Markdown 内容快照和只新增 frontmatter tags 的安全边界。`0.4` 完整操作历史是下一阶段。

已实现：

- 新增文件夹生成与最近批次整体回退命令；
- 默认当前笔记父文件夹，支持任意文件夹、库根目录和递归开关；
- 单批上限默认 50，可配置为 1–200，超过上限阻断且不截断；
- API key 与活动 Markdown 前置失败时保持零读取、零索引、零请求；
- frontmatter 和 inline tags 汇总为整篇标签清单，inline 缺失项默认同步到 frontmatter，但正文不改写；
- 最多 2 个并发 AI 请求，支持立即取消、丢弃晚到结果和仅重试失败项；
- AI 失败时保留本地 inline 同步项；
- 逐笔记展示 frontmatter、inline、AI 来源与前后 tags；
- 低风险项默认选中，新标签中风险逐项选择，高风险动作不可执行；
- 二次确认后执行全量预检、逐文件 CAS 和逆序补偿；
- 批次意图、应用、回退与固定 before/after 恢复目标可跨插件重载持久化；
- 完整 Markdown SHA-256 或 tags 漂移时保持整批零写入。

验收标准：

- 用户能清楚看到哪些文件会被修改；
- 默认只勾选低风险建议；
- 应用前可以取消；
- 应用后可以按批次撤销；
- 大文件夹不会让 Obsidian 长时间无响应。

### 4.3 0.4：增强撤销和操作历史

目标：让用户敢于在更大范围使用插件。

需求：

- 操作历史列表；
- 按操作查看影响文件；
- 按操作撤销；
- 区分当前笔记操作和批量操作；
- 记录操作来源、时间、模型、设置快照；
- 对已经手动修改过的文件给出撤销冲突提示。

验收标准：

- 用户能找到最近的插件写入历史；
- 批量操作可以整体撤销；
- 文件内容已变化时，不盲目覆盖用户后续修改。

### 4.4 0.5：增量索引和大型库性能

目标：让插件在大型库中稳定可用。

需求：

- 监听文件变更，增量更新 tag index；
- 区分索引过期和索引可用状态；
- 提供索引刷新进度；
- 限制每个标签代表性示例数量；
- 支持跳过大文件或特定目录；
- dev 模式展示更细阶段耗时。

验收标准：

- 大型库启动时不自动长时间扫描；
- 普通推荐请求不重复读取全库；
- 用户能知道索引是否过期；
- 索引刷新失败不会破坏已有缓存。

### 4.5 0.6：本地和多 Provider 支持

目标：降低用户的隐私顾虑和使用成本。

需求：

- 支持 Ollama 或其他本地 OpenAI-compatible endpoint；
- 为常见 provider 提供配置预设；
- 区分 Chat Completions 兼容和其他格式；
- 增加 provider 测试按钮；
- 在设置页提示哪些内容会发送给 AI。

验收标准：

- 用户能用 DeepSeek、OpenAI、本地兼容服务完成推荐；
- 配置错误时能得到明确错误；
- 用户知道当前笔记内容和标签索引摘要会被发送给 provider。

## 5. 暂缓范围

这些能力有价值，但不进入 MVP 完整版，也不作为近期优先级：

- 标签图谱可视化；
- embedding 向量索引；
- 自动定时清理；
- 云端同步或账号系统；
- 多用户协作；
- 全文语义搜索；
- AI 自动重写笔记内容；
- 移动端专项适配；
- 插件市场正式发布流程自动化。

## 6. 当前优先级

建议下一步只做一件事：**0.4 完整操作历史**。

理由：

- 当前笔记推荐、库级健康报告、受审查 inline 清理和文件夹安全批次四个闭环已经完成实现；
- recommendation、batch 与 cleanup V2 已共享未解决事务门禁，但用户仍缺少统一的历史列表和按记录检查入口；
- 下一阶段应把现有安全记录统一展示，不继续扩大正文或文件夹动作类型；
- inline 新增、删除、拆分、模糊/全局替换、AI 正文写入和后台静默执行继续不做。

推荐实施顺序：

1. 创建中文 OpenSpec change，明确历史列表、筛选、详情和记录保留边界；
2. 统一展示 recommendation、legacy cleanup、cleanup V2 和 folder batch 的类型与状态；
3. 为每类记录提供只读详情、作用文件、状态和可用动作；
4. 保持既有 V2 固定恢复目标和全局门禁，不从历史 UI 绕过安全检查；
5. 增加单元测试、端到端回归和真实库 smoke test，再决定后续增量索引方向。
